# Performance

## The claim, and its limits

`bamsplit chrom` reads a coordinate-sorted BAM **once**. The `samtools view` loop
everyone uses opens it once per chromosome:

```bash
for chr in $(samtools idxstats in.bam | cut -f1); do
    samtools view -b in.bam "$chr" > "$chr.bam"
done
```

Be precise about what that costs. With an index, each of those opens *seeks* to
one reference's chunks rather than decompressing the whole file, so the loop is
not eight full passes — it is closer to one pass plus eight process startups and
eight index loads. The structural differences that remain are real but narrower
than "N passes versus one":

* the loop **requires** an index; `bamsplit chrom` does not;
* the loop cannot express `shard`, `tag`, or `region` at all;
* one `bamsplit` invocation writes every output, so there is one manifest, one
  atomic commit, and one conservation check rather than N unrelated files.

Everything else — mmap, thread count, the indexed engine, raw transfer —
**must be benchmarked on your data before you believe it.**
`scripts/benchmark.sh` exists so you can, and [Measured results](#measured-results)
below is one such run, reported in full including where `bamsplit` loses.

```console
cargo build --release
scripts/benchmark.sh sample.bam "1 2 4 8 16" [annotation.bed]
```

It reports wall time, CPU time, peak RSS, records/s, input B/s, output bytes,
compression ratio, file count, and input opens for the samtools baseline and for
several `bamsplit` configurations. Each `bamsplit` row pins `--engine`
explicitly, so a row that names one variable moves only that variable.

## Measured results

One run, on one machine, on one synthetic input. Read the caveats before
quoting anything here.

**Machine.** AMD Ryzen 7 5700X (8 cores / 16 threads), 125 GiB RAM, Linux
6.14.5 (Fedora 40), rustc 1.94.1, `--release`. Input, outputs, and temporary
files all on **tmpfs** — a RAM disk. That deliberately removes storage from the
measurement so the numbers reflect CPU and algorithm rather than the reviewer's
SSD; it also means every conclusion below about `--io mmap` and the indexed
engine is a *best case*, because random access costs nothing here.

**Input.** 306,099,070 bytes, 2,000,000 records, 8 references, coordinate-sorted,
150-base reads with `RG` and `NM` tags, BAI index present. Generated by
`cargo run --release --bin bamsplit-generate-fixtures -- --benchmark 8 250000 bench.bam`,
which fills sequence and quality with a pseudo-random stream so DEFLATE has real
work to do. The default fixtures use `=` bases and "quality unavailable", which
compress to nearly nothing and would make any compression benchmark meaningless.

**Baseline.** `samtools 1.15.1` / htslib 1.15.1, the `samtools view` loop above.
Both sides write BGZF at level 6. Note that samtools `-@N` requests N
*additional* threads while `bamsplit --threads N` is a total budget, so the
samtools rows have a slight thread advantage at every N.

### `chrom`, scaling with threads

| threads | samtools loop | bamsplit `stream` | bamsplit `stream` CPU |
| ---: | ---: | ---: | ---: |
| 1 | 9.44 s | **7.69 s** | 7.65 s |
| 2 | 4.82 s | 7.54 s | 7.50 s |
| 4 | 2.58 s | 5.42 s | 8.61 s |
| 8 | 1.66 s | 2.28 s | 9.73 s |
| 16 | 1.57 s | 1.78 s | 11.96 s |

`bamsplit` wins single-threaded and loses everywhere else. Two honest reasons:

* **`--threads 2` buys nothing.** `ThreadBudget::for_total` spends one thread on
  routing and splits the rest one-third/two-thirds between inflate and deflate.
  At a budget of 2 that leaves one compression thread — the same as `-t1` — while
  still asking the OS for three. The measurement (7.54 s versus 7.69 s) is the
  cost of that rounding, and it is the clearest evidence for the fixed-split
  entry in [Known performance debt](#known-performance-debt).
* **The samtools loop parallelizes across processes.** Eight independent
  `samtools view` invocations each get `-@N`, so the loop's effective width is
  larger than the number the column says.

Peak RSS stayed between 7.4 MB (`-t1`) and 15.2 MB (`-t16`) for the streaming
engine, against 4.8–22.3 MB for the samtools loop. Both are effectively constant
in input size; neither is a differentiator.

### `chrom`, one variable at a time (4 threads)

Every row below differs from `stream -t4` (5.42 s) in exactly one way.

| configuration | wall | output bytes | note |
| --- | ---: | ---: | --- |
| `--engine stream` | 5.42 s | 280,052,534 | the reference row |
| `--index none` | 5.47 s | 280,053,326 | BAI construction is **free** at this scale |
| `--io mmap` | 5.37 s | 280,056,664 | no gain for a sequential pass; RSS 305 MB |
| `--compression-level 1` | 3.76 s | 415,806,762 | 1.44x faster, 48% larger |
| `--engine spool` | 3.45 s | 280,055,650 | |
| `--engine indexed` | **2.04 s** | 280,054,799 | 2.7x faster than `stream` |
| `--engine auto` | 2.01 s | 280,054,241 | picked `indexed` |

Three of these contradict what this document used to assert, so they are worth
stating plainly:

* **Index construction did not cost measurably anything** — 5.47 s against
  5.42 s, inside run-to-run noise. Skipping it is a smaller lever than the old
  text implied.
* **Level 1 was 1.44x faster here, not 3–4x, and 48% larger, not 10–15%.** The
  old numbers were plausible and unmeasured; these are measured. The speedup is
  thread-dependent — 1.74x at `--threads 1`, 2.09x for the in-memory round trip
  — because compression is the part that parallelizes. See
  [`--compression-level`](#--compression-level) for all three.
* **`--io mmap` did not help the streaming engine**, exactly as the design
  predicts, and it cost 305 MB of resident mapping to prove it. It is selected
  by `--io auto` only for the indexed engine, and that remains correct.

`samtools` produced 279,691,081 bytes to `bamsplit`'s 280,052,534 — **0.13%**
larger at the same nominal level, which is as close as two independent DEFLATE
implementations get. It was 4.2% before the backend change described next.

### The DEFLATE backend

`flate2`'s default backend is `miniz_oxide`. Switching to `zlib-rs` (a pure-Rust
port of zlib-ng, enabled unconditionally in the workspace manifest) was measured
on the same input, same commands, `--index none --no-pg`:

| threads | `miniz_oxide` | `zlib-rs` | speedup |
| ---: | ---: | ---: | ---: |
| 1 | 15.34 s | 7.52 s | 2.04x |
| 4 | 9.25 s | 5.42 s | 1.71x |
| 16 | 2.83 s | 1.75 s | 1.62x |
| output | 291,401,636 B | 280,052,822 B | 3.9% smaller |

Faster *and* smaller at the same nominal level 6, with no C toolchain and no
`unsafe` in this crate. Before the change `bamsplit -t1` took 15.34 s against
samtools' 9.44 s; after it, 7.69 s — so essentially the whole original
single-thread deficit was the compressor, not the pipeline around it, and the
output-size gap against htslib went from 4.2% to 0.13%.

This is the sort of thing a benchmark is for. Nothing about the pipeline changed;
the default backend was simply the wrong one, and only a measurement against an
external baseline made that visible.

### `region`, and the per-region query plan

200 regions of 10 kb each — 2 Mb of a 2 Gb declared genome, holding 7.9% of the
records — with `--assignment overlap`, 4 threads:

| engine | wall | records read | outputs |
| --- | ---: | ---: | ---: |
| `stream` | 1.61 s | 2,000,000 | 200 |
| `spool` | 1.49 s | 2,000,000 | 200 |
| `indexed` | **0.15 s** | **157,098** | 200 |
| `auto` | 0.16 s | 157,098 | 200 |

**10.7×**, and the reason is in the second column: the per-region plan read 7.9%
of the records because that is all its queries reached. Note that the streaming
and spool rows are already cheap in absolute terms — they write only the same
157,098 records — so the 10.7× is the cost of *reading and discarding* the other
92%, which is exactly what the query plan removes. This is the case the
plan exists for. All three engines produced byte-identical outputs (verified
with `--no-pg --index none`, so the `@PG` line does not differ).

With a *dense* annotation — 8 regions covering half the declared genome — the
planner prefers `stream`, and on this input that costs it:

| engine | wall |
| --- | ---: |
| `auto` (picked `stream`) | 5.50 s |
| `stream` | 5.34 s |
| `indexed` | **2.00 s** |

The indexed engine reads everything here too, but it reads it as eight parallel
per-reference tasks. The planner's density-first rule is deliberately
conservative — it is protecting the many-small-contigs and network-storage cases
that this tmpfs, 8-reference input is the exact opposite of — but on an input
shaped like this one, `--engine indexed` is worth passing by hand. See
[Known performance debt](#known-performance-debt).

### The `end_to_end` harness

`cargo bench --bench end_to_end` runs the same pipeline on smaller in-process
fixtures, which is what a CI regression check can afford. Its numbers agree with
the whole-run measurements above, which is the point of having both.

| group | result |
| --- | --- |
| `chrom_threads` (32 k records, 8 refs) | 75.1 ms at 1 thread, **74.0 ms at 2**, 60.0 at 4, 30.8 at 8, 23.4 at 16 |
| `chrom_engines` (level 1) | `stream` 36.9 ms, `spool` 29.6 ms |
| `chrom_indexing` (level 1) | `bai` 23.7 ms, `none` 22.8 ms — index costs 3.9% |
| `chrom_contigs` (40 k records, 4 threads) | 4 refs 44.7 ms, 64 refs 53.8 ms, 512 refs 106.3 ms |
| `shard --key qname` | 8 shards 24.5 ms, 64 shards 28.9 ms |

Two things worth reading off that table. `chrom_threads` reproduces the
`--threads 2` stall independently, on a different input and a different harness.
And `chrom_contigs` prices the many-outputs case: the same 40,000 records cost
**2.4×** as much split 512 ways as split 4 ways, all of it per-output overhead —
descriptor churn, index finalization, and the atomic rename per file. That is
the concrete reason the planner will not choose the indexed engine above 64
references.

### Reproducing exactly

```console
cargo build --release
cargo run --release --bin bamsplit-generate-fixtures -- --benchmark 8 250000 /tmp/bench.bam
samtools index -@ 8 /tmp/bench.bam
scripts/benchmark.sh /tmp/bench.bam "1 2 4 8 16" /path/to/annotation.bed
```

## Where the time goes

```console
cargo bench --bench core
```

Measured on the machine described above, 20,000 records of 150 bases with a
seeded (realistically compressible) payload, single-threaded:

| stage | per run | per record | share of a level-6 round trip |
| --- | ---: | ---: | ---: |
| read only (inflate + framing) | 6.17 ms | 309 ns | 15% |
| read + write, level 0 | 8.06 ms | 403 ns | — |
| read + write, level 1 | 19.26 ms | 963 ns | — |
| read + write, level 6 | 40.28 ms | 2 014 ns | 100% |

Subtracting gives the ordering, and it is stable:

1. **BGZF deflate** dominates — 32.2 ms of the 40.3 ms level-6 round trip, or
   **80%**. It is why `--compression-level` is the single biggest lever and why
   the streaming engine spends most of its thread budget on the writer.
2. **BGZF inflate plus framing** is second at 6.17 ms, about a fifth of deflate.
3. **The BGZF container itself** — block headers, CRCs, the `memcpy` into the
   reusable buffer — is 1.89 ms, the gap between read-only and level 0.
4. **Routing** is noise. `xxh3_shard` measured 3.97 ns per record, so sharding
   20,000 records costs 0.08 ms against a 40 ms round trip: **0.2%**. `chrom`,
   which reads four bytes, is cheaper still.

Individual operations, for reference: `record/fixed_core` 1.54 ns,
`record/qname` 2.86 ns, `cigar/reference_span` 6.32 ns,
`cigar/aligned_blocks_reuse_buffer` 7.83 ns against
`cigar/aligned_blocks_collect` 23.5 ns (the reusable buffer is worth 3×),
`record/tag_lookup_first` 36.3 ns rising to `tag_lookup_last` 61.6 ns,
`routing/filename_encode_plain` 45.6 ns.

That ordering is what justifies the raw-record path: since routing is nearly
free, anything spent decoding fields nobody asked for is pure overhead. The
`transfer` group measures it directly — raw transfer of 5,000 records took
71.4 µs against 462.6 µs to parse every field and re-encode, a **6.5× gap**, and
that gap is the saving on every record the router does not need to look at.

One caveat on these micro-numbers. They are single-threaded and I/O-free, so
deflate's 80% share is its *maximum*. In the whole-run measurements above, at
`--threads 4`, compression is spread across workers and dropping from level 6 to
level 1 bought only 1.44× rather than the 2.09× the round trip predicts.

## Tuning

### `--compression-level`

The dominant cost, though by less than folklore suggests. Measured three ways on
the data in [Measured results](#measured-results), level 1 against level 6:

| measurement | speedup |
| --- | ---: |
| single-threaded round trip, in memory (`cargo bench`) | 2.09× |
| whole run, `--threads 1` | 1.74× |
| whole run, `--threads 4` | 1.44× |

Output was **48% larger** in every case (415.8 MB against 280.1 MB). The gain
shrinks as threads are added, because compression is the part that parallelizes
and everything else is already serial. For intermediate files a pipeline deletes
an hour later, level 1 is still a good trade; for anything archived it is not,
and at high thread counts it buys much less than the folklore 3–4×.

```console
bamsplit chrom in.bam --out-dir out --compression-level 1
```

### `--threads`

A **total** budget. The streaming engine keeps one output open, so nearly all of
it goes to that writer's compression — which is the bottleneck, so scaling is
good up to the point where inflate or storage saturates.

Output is **byte-identical regardless of thread count**, verified at 1, 2, 4, 8,
and 16 threads on the input above. Block boundaries fall at fixed uncompressed
offsets and compression settings do not depend on scheduling, so a benchmark
cannot be confounded by nondeterministic output.

One caveat, and it will bite anyone diffing output files: the `@PG` record
embeds the full command line, *including* `--threads`, so two runs at different
thread counts differ in the header — and because DEFLATE is content-sensitive,
that can shift the compressed length of the first block by a few bytes. Compare
with `--no-pg` on both sides, or compare decoded records rather than bytes.

Note also that the split rounds badly at small budgets: `--threads 2` measured
the same as `--threads 1`, because one thread routes and the remainder leaves a
single compression worker. Go from 1 to 4, not 1 to 2.

### `--index none`

Index construction walks bins and a linear index per record, so it is not free
in principle — but it barely shows up in measurement. On the whole-run 2 M-record
split at level 6 it was 5.47 s with the index against 5.42 s without, inside
run-to-run noise. The `chrom_indexing` micro-benchmark, which uses level 1 and so
gives compression far less to hide behind, puts it at 23.68 ms against 22.80 ms —
**3.9%**.

That is the honest range: a few percent when output compression is cheap,
invisible when it is not. Skip it if the downstream step does not query by
coordinate, but do not budget the time back.

### `--engine indexed`

Sometimes faster, sometimes much slower. Faster when: few large references, fast
local storage, plenty of threads. Slower when: many small contigs (chunk
boundaries mean blocks get inflated by two tasks), or network storage (random
access defeats read-ahead).

On the 8-reference tmpfs input in [Measured results](#measured-results) it was
**2.7× faster** than `stream` at the same thread count (2.04 s against 5.42 s),
because eight per-reference tasks fill the thread budget better than one writer
does. That is the shape it is good at, and it is also the shape least like a
network-mounted 3,000-contig assembly.

`--engine auto` requires *both* a local indexed file and at most 64 references
before it will choose `indexed`. Override deliberately, and measure.

### `--io mmap`

**A mapping does not avoid decompression.** BAM records inside it are still
BGZF-compressed. What it buys is one fewer copy per block and cheap independent
cursors, which only matters for the indexed engine's random access. `--io auto`
selects it there and nowhere else.

Measured on the streaming engine, where `--io auto` would not select it: 5.37 s
against 5.42 s buffered — no gain, and 305 MB of resident mapping to show for
it. That is the expected result, not a surprise, and it is why `auto` reserves
mmap for the indexed engine.

On network filesystems mapping is frequently *slower*, and on some it fails
outright — in which case `bamsplit` falls back to buffered I/O unless mmap was
requested explicitly.

### `--max-open-files`

Only relevant when many outputs are live at once. Parking is cheap — one block
flush — so a low limit costs little; the default of 64 is comfortable under a
1 024-descriptor `ulimit`.

## Engine characteristics

| | stream | indexed | spool |
| --- | --- | --- | --- |
| input passes | 1 | 1 logical, random physical; under `region`, only the queried chunks | 1 read + 1 replay |
| peak memory | ~constant | ~constant × workers | ~constant |
| open descriptors | 1 | workers | bounded by `--max-open-files` |
| temporary storage | none | none | ≈ uncompressed record volume |
| parallelism | one writer, many compression threads | one task per reference (per-region queries merged into it) | one task per output |
| needs an index | no | yes | no |
| works on stdin | yes | no | yes |
| tolerates unsorted input | no (detects and falls back) | no | yes |
| serves `region` | yes | yes, via the per-region query plan | yes |
| serves `shard` / `tag` | yes | **no**, refused | yes |

## Reproducing a measurement

```console
cargo build --release

# Micro-benchmarks, with statistical comparison against the previous run.
cargo bench --bench core
cargo bench --bench end_to_end

# Whole-run comparison against samtools on real data. A third argument adds a
# `region` section across the engines.
scripts/benchmark.sh /path/to/sample.bam "1 2 4 8 16" /path/to/annotation.bed

# Correctness, which is the precondition for any performance claim.
scripts/differential-test.sh /path/to/sample.bam
```

Datasets worth covering, because they stress different parts:

* short reads, high coverage — record framing and deflate dominate
* long reads (ONT/PacBio) — larger records, fewer of them; CIGAR work grows
* RNA-seq with spliced CIGARs — exercises `N` handling
* a few large chromosomes — the indexed engine's best case
* many small contigs — the indexed engine's worst case
* local NVMe versus network storage — flips the mmap and indexed decisions

## Region routing

Annotation loading is a fixed up-front cost proportional to the annotation, not
to the BAM: a full GENCODE GTF is a few hundred thousand records and loads in
under a second. What varies per record is the index query plus the segment
verification.

The index query is a binary search plus a short backwards walk. The verification
is a two-pointer sweep over the read's aligned blocks against the region's
segments, so it is linear in `blocks + segments` rather than their product —
which matters because a spliced read against a many-exon transcript is exactly
the case where the naive nested loop gets expensive.

`--assignment overlap` writes each matching record once *per* region. A read
overlapping twelve transcripts costs twelve writes, and the output volume grows
accordingly; the manifest's `duplicate_emissions` is how you find out how much.

The one lever that changes the *order* of the cost is engine choice. Against a
sparse annotation the indexed engine's per-region query plan skips whatever the
queries do not reach — measured at 10.7× on 200 regions covering 7.9% of a
2 M-record BAM. Against a dense one it reads everything anyway, and the only
gain left is per-reference parallelism. See
[Measured results](#measured-results) for both.

## Known performance debt

* **Spool finalization is serialized.** Each output already spreads its
  compression across the shared pool, so adding task-level parallelism on top
  would exceed the thread budget without a proper scheduler.
  `ThreadBudget::for_tasks` is what a concurrent finalizer would consume.
* **The indexed engine re-inflates boundary blocks.** A block holding the last
  `chrN` record and the first `chrN+1` record is inflated by both tasks. Bounded
  and small for large references; pathological for thousands of tiny contigs,
  which is why the planner refuses to choose `indexed` there.
* **The thread budget rounds badly at 2.** `ThreadBudget::for_total` reserves one
  thread for routing and splits the rest one-third/two-thirds, so a budget of 2
  yields one compression worker — measurably identical to `--threads 1` (7.54 s
  against 7.69 s) while requesting three threads from the OS. A budget-aware
  split would either give the writer both threads or decline the routing
  reservation.
* **The region planner prefers `stream` for dense annotations even when
  `indexed` would win.** Measured: 5.50 s against 2.00 s on eight large
  references over local storage. The rule is protecting the many-small-contigs
  and network-storage cases, and it has no way to tell them apart from this one
  without probing. `--engine indexed` is the deliberate override.
* **The unplaced tail scan is sequential.** A binning index cannot address
  unplaced records, so they need one pass from the last reference's first record.
  Skipped entirely when the index reports no unplaced records.
* **Input inflation shares its thread pool with nothing.** `--threads > 1`
  does select `noodles`' multi-threaded BGZF reader, but the split between
  inflation and deflation is a fixed one-third/two-thirds rather than measured.
  On an input that is unusually cheap to deflate — level 0 output — the ratio is
  wrong, and nothing rebalances it.
* **Scaling past 8 threads is poor.** 2.28 s at 8 threads, 1.78 s at 16, against
  9.73 s and 11.96 s of CPU respectively: the extra threads are burning cycles
  for a 1.28× return. One writer with a batch of parallel block compressions
  has a serial fraction — staging, sealing, and offset resolution — that Amdahl
  eventually collects on. Splitting the writer would mean giving up the
  single-pass guarantee, so this is a design cost, not an oversight.
